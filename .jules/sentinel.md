## 2025-08-02 - Securing Third-Party Dynamic Embeds in Client-Side State
**Vulnerability:** The portfolio application allows users to dynamically load arbitrary web pages in an `<iframe>` by entering a URL stored in `localStorage`. Without proper protocol and domain validation, this is susceptible to phishing, clickjacking, or Cross-Site Scripting (XSS) if the storage is compromised or manipulated. Additionally, third-party iframes lacked standard HTML `sandbox` attributes, permitting unrestricted script execution, popups, and potential top-frame navigation.

**Learning:** This architectural gap existed because dynamic integration features were implemented for ease of testing local Notion workspace documents without anticipating client-side security boundary validation. Furthermore, modern `sandbox` attributes on frames are frequently omitted to avoid styling or capability frictions during development, leaving embeds overly privileged.

**Prevention:** Always restrict dynamically loaded resources to strict HTTPS protocols and validated domains (such as notion.com, notion.site, notion.so, or v1.embednotion.com) before loading them into frame states. In addition, apply defense-in-depth measures by configuring the `sandbox` attribute (e.g., `sandbox="allow-scripts allow-same-origin allow-forms allow-popups"`) to restrict frame capabilities to only what is strictly necessary.
