# Application System and Tracker

## 0. Purpose

This file defines the operating system for Alexander Woodcock Salomón’s international job search.

The goal is not to “apply more.” The goal is to run a controlled pipeline that converts the existing portfolio assets, especially TwinSight X500, into interviews, offers, contractor opportunities, and market feedback.

This system assumes the previous strategic decisions are already fixed:

- Primary target: Real-Time 3D / Interactive Technical Visualization / Unity WebGL.
- Secondary target: Unity Technical Artist focused on optimization, runtime systems, tools, shaders, and CAD-to-realtime workflows.
- Expansion target: Digital Twin / Simulation / XR / Industrial Visualization.
- Controlled secondary route: Tools / Python Automation / AI-assisted production tooling.
- Fallback routes: Full-stack and 3D generalist only when strategically useful.
- Current priority: remote from Colombia.
- Future mobility: Portuguese passport expected in approximately two years; Germany route possible through legal marriage and residence with German partner.

This section is operational. It does not redefine the positioning. It translates the strategy into execution.

---

## 1. Core operating principle

The job search must be treated as a pipeline, not as scattered applications.

Every target should move through a controlled sequence:

```text
Target identified → Fit scored → Evidence selected → Application customized → Outreach sent → Follow-up → Interview → Test → Offer → Decision → Retrospective
```

The system must prevent four failure modes:

1. Applying to roles without enough fit.
2. Spending too much time customizing low-probability applications.
3. Over-positioning into roles where the evidence is weak.
4. Losing track of companies, conversations, follow-ups, and feedback.

The tracker is the source of operational truth.

## 2. Application categories

All opportunities must be classified before applying.

## 2.1 Category A — High-fit targets

These are the highest-priority opportunities.

They match TwinSight directly and do not require major repositioning.

Examples:

- Interactive 3D Developer.
- Real-Time 3D Developer.
- Unity WebGL Developer.
- Technical Visualization Developer.
- Digital Twin Visualization Developer.
- Simulation Visualization Developer.
- Unity Developer for enterprise 3D.
- XR Developer for industrial or training applications.

A Category A opportunity should satisfy most of these conditions:

- Unity, WebGL, real-time 3D, simulation, digital twin, XR, or technical visualization is central to the role.
- A technical portfolio case study is relevant.
- TwinSight can be used as the primary proof.
- Remote, contractor, LATAM, or global work is plausible.
- The role does not require senior commercial experience as a hard gate.
- The company works in industrial, education, simulation, XR, training, product visualization, or enterprise 3D.

Application effort: high.

Customization level: strong.

Expected weekly volume: 5–8.

---

## 2.2 Category B — Adjacent targets

These are plausible but require adaptation.

Examples:

- Unity Technical Artist in games.
- Game Technical Artist.
- Shader Technical Artist.
- Tools Developer.
- Pipeline Developer.
- 3D product configurator developer.
- WebGL / Three.js Developer.
- Python Automation Developer.
- AI Tools Developer.

A Category B opportunity is valid when:

- The role is related to the portfolio but not a direct TwinSight match.
- ARA, Blender portrait, or shader work may support the application.
- Some missing skills exist, but the gap is not fatal.
- The application can be made credible without exaggeration.

Application effort: medium.

Customization level: moderate.

Expected weekly volume: 8–12.

---

## 2.3 Category C — Volume targets

These are lower-fit but useful for market testing, interview practice, or income fallback.

Examples:

- Junior Unity Developer.
- C# Developer with light Unity.
- Full-stack developer.
- Python automation support.
- Freelance web projects.
- 3D generalist roles.
- Simple contractor gigs.

A Category C opportunity is acceptable when:

- It can produce income quickly.
- It does not consume excessive customization time.
- It does not force a false professional identity.
- It can be applied to with a lighter version of the CV.

Application effort: low.

Customization level: minimal.

Expected weekly volume: 10–20.

---

## 2.4 Watchlist targets

These are not immediate targets but should be monitored.

Examples:

- Senior Technical Artist AAA.
- Senior Simulation Engineer.
- Digital Twin Architect.
- Research Engineer.
- Graphics Programmer.
- AI Engineer.
- EU-only roles requiring current EU work authorization.
- Germany-only roles requiring German language.

Watchlist targets should not consume active application time unless a specific opening unusually matches the profile.

## 3. Weekly application mix

A balanced weekly target should avoid both over-customization and indiscriminate spam.

Recommended baseline after the thesis defense:

| Category | Weekly target |
|---|---:|
| A | 5–8 |
| B | 8–12 |
| C | 10–20 |
| Speculative outreach | 10–15 |
| Recruiter contacts | 5–10 |

Total weekly outbound actions:

```text
Minimum controlled pace: 30 actions/week
Strong pace: 45–55 actions/week
Aggressive pace: 60–75 actions/week
```

An outbound action means one of the following:

- Submitted application.
- Recruiter message.
- Founder / technical lead outreach.
- Referral request.
- Follow-up.
- Portfolio feedback request.
- Community post with job-search relevance.

Do not count passive browsing as execution.

## 4. Daily execution blocks

The job search should be split into repeatable blocks.

## 4.1 Minimum daily block

Use this when time or energy is limited.

```text
Duration: 90 minutes

1. Review tracker: 10 min
2. Find opportunities: 20 min
3. Apply or message: 40 min
4. Update tracker: 10 min
5. Next-action planning: 10 min
```

Expected output:

- 2–4 applications or messages.
- Tracker updated.
- No loose tabs left open.

---

## 4.2 Standard daily block

Use this as the default after defense.

```text
Duration: 3 hours

1. Pipeline review: 15 min
2. Target search: 30 min
3. Custom applications: 75 min
4. Outreach/follow-up: 30 min
5. Tracker update: 15 min
6. Portfolio/CV adjustment: 15 min
```

Expected output:

- 4–8 outbound actions.
- 1–2 high-quality customized applications.
- Follow-ups sent on schedule.

---

## 4.3 Deep work block

Use this 2–3 times per week for strategic assets.

```text
Duration: 2–4 hours

Allowed work:
- TwinSight case study refinement.
- Demo video update.
- GitHub README polish.
- Portfolio section improvement.
- Technical test preparation.
- Interview rehearsal.
```

This block is not for browsing job boards.

## 7.2 Fit columns

Use these scoring fields to prevent bad applications.

| Field | Scale |
|---|---:|
| Role fit | 1–5 |
| Portfolio fit | 1–5 |
| Remote feasibility | 1–5 |
| Compensation potential | 1–5 |
| Probability | 1–5 |
| Priority | A / B / C |

Scoring rule:

```text
Total score = Role fit + Portfolio fit + Remote feasibility + Compensation potential + Probability
```

Interpretation:

| Score | Meaning |
|---|---|
| 21–25 | Strong target |
| 17–20 | Apply selectively |
| 13–16 | Low effort only |
| <13 | Do not apply |

## 15. Application quality gates

Before applying, check these gates.

## 15.1 Mandatory gate

Do not apply if all are true:

- Requires current US/EU work authorization.
- Does not allow remote or contractor work.
- Requires 5+ years formal industry experience.
- Has no connection to Unity, 3D, simulation, XR, WebGL, tools, or Python.
- Would require a false claim.

---

## 15.2 Apply anyway gate

Apply despite imperfect fit if at least three are true:

- TwinSight is directly relevant.
- Remote scope is worldwide, LATAM, or contractor-friendly.
- Requirements are flexible.
- Role is junior, mid-junior, associate, contractor, or project-based.
- Company works in simulation, digital twin, XR, education, product visualization, or industrial 3D.
- The application can be customized in less than 45 minutes.

## 17.2 Conversion metrics

| Metric | Good signal |
|---|---:|
| Response rate | >8% |
| Recruiter screen rate | >3% |
| Interview rate | >2% |
| Technical test rate | >1% |
| Offer rate | >0.3% |

- Positioning is too broad.
- CV is weak.
- Portfolio is not accessible enough.
- Wrong roles are being targeted.
- Applications are going to local-only jobs.
- Outreach is missing.

## 18.2 Weekly decision rules

If there are no responses after 50 applications:

- Review CV headline.
- Review portfolio homepage.
- Add demo video thumbnail.
- Improve TwinSight summary.
- Increase direct outreach.

If there are responses but no interviews:

- Check salary expectation.
- Check work authorization wording.
- Check whether the role requires experience not shown.
- Improve project explanation.

If there are interviews but no progress:

- Improve verbal explanation.
- Prepare technical breakdown.
- Practice AI-assisted development disclosure.
- Prepare code and architecture discussion.

If there are technical tests but poor performance:

- Create a skill sprint.
- Reduce application volume temporarily.
- Focus on Unity/C#/WebGL fundamentals.

## 19. Monthly review

At the end of every month, classify the job search.

## 19.1 Outcome categories

```text
Healthy pipeline:
- Responses arriving.
- Some recruiter screens.
- Some interviews.
- No major positioning contradiction.

Weak pipeline:
- Low responses.
- Few interviews.
- Applications mostly ignored.

Wrong market:
- Roles require US/EU authorization.
- Remote is not actually worldwide.
- Seniority mismatch is frequent.

Wrong evidence:
- Recruiters ask for commercial experience.
- Portfolio does not show enough proof.
- TwinSight not immediately understood.
```

---

## 19.2 Monthly adjustment rules

After 30 days:

- Keep applying if response rate is acceptable.
- If no response, revise CV and portfolio front page.
- If roles reject due to authorization, shift toward LATAM contractor and global contractor platforms.
- If roles reject due to experience, increase project-based outreach.
- If roles reject due to skill gaps, schedule a focused sprint.

After 60 days:

- Double down on the top two responding role families.
- Stop applying to low-response categories.
- Use feedback to rewrite positioning.
- Increase direct outreach and referral attempts.

After 90 days:

- Reassess salary target.
- Consider contractor/freelance bridge work.
- Consider temporary fallback route if no traction.
- Decide whether to invest more in ARA, WebGL, XR, or Unity Technical Art.

## 20. Bad-offer rejection criteria

Reject or negotiate offers with these red flags.

## 20.1 Structural red flags

- No written contract.
- Unclear payment terms.
- Payment only after vague milestones.
- Full-time exclusivity for low contractor pay.
- Fixed schedule but no employee benefits.
- Required unpaid test longer than 4–6 hours.
- No clarity on IP ownership.
- No clarity on termination terms.
- Salary below minimum target without learning value.

---

## 20.2 Remote-work red flags

- “Remote” but requires local work authorization.
- “Remote” but demands relocation soon without support.
- “Contractor” but requires employee-like control.
- No mention of payment currency.
- No invoicing process.
- No tax documentation.
- No equipment clarity.

---

## 20.3 Portfolio/IP red flags

- Requests full project files before contract.
- Asks to recreate TwinSight-like work for free.
- Requires confidential unpaid work.
- Claims ownership of test work without compensation.
- Requests manufacturer/CAD assets without legal clarity.

---

## 21. Offer evaluation framework

Evaluate every offer using six dimensions.

| Dimension | Weight |
|---|---:|
| Net income | 30% |
| Role fit | 20% |
| Portfolio leverage | 15% |
| International leverage | 15% |
| Stability | 10% |
| Learning value | 10% |

Use this scoring:

```text
5 = excellent
4 = strong
3 = acceptable
2 = weak
1 = unacceptable
```

Any offer below 3/5 in both net income and role fit should be rejected unless there is an urgent financial need.

## 22. Gross-to-net tracking

Track compensation as gross and estimated net.

Required fields:

| Field | Example |
|---|---|
| Gross monthly | USD 3,000 |
| Payment currency | USD |
| Platform fee | 0–5% |
| Conversion spread | 0–3% |
| Social security reserve | Estimate |
| Tax reserve | Estimate |
| Net estimate | Conservative |

Do not compare offers only by gross salary.

A USD 3,000 contractor offer may be weaker than a lower employee offer if it has unstable payments, no benefits, and high compliance cost.

## 27. Technical test handling

Before accepting a test, record:

- Expected time.
- Deadline.
- Compensation.
- IP ownership.
- Scope.
- Tools required.
- Evaluation criteria.

Reject or negotiate unpaid tests that require excessive time or production-quality deliverables.

Suggested rule:

```text
Accept unpaid test: ≤4 hours
Question unpaid test: 4–8 hours
Reject or negotiate: >8 hours
```

Exception: a high-fit, high-salary Category A opportunity may justify a longer test if the scope is clearly bounded.

## 30. Anti-dispersion rules

The main operational risk is not lack of opportunities. It is fragmentation.

Rules:

1. Do not create a new portfolio project unless it supports an observed market gap.
2. Do not rewrite LinkedIn every week.
3. Do not change positioning after a few rejections.
4. Do not apply to roles that require false claims.
5. Do not study German, Houdini, AI, WebGL, React, and Unreal at the same time.
6. Do not polish low-priority projects before TwinSight is publicly strong.
7. Do not treat browsing as work.
8. Do not measure progress by tabs opened.

## 34. Final operational recommendation

The initial target is not to find the perfect job. The initial target is to generate enough market signal to know which version of the profile is converting.

The first 100 outbound actions should be treated as a calibration period.

After 100 outbound actions, evaluate:

```text
1. Which role family responds?
2. Which market responds?
3. Which salary range responds?
```
